## What changed

- **New record** `docs/solutions/harness/committed-diff-scoped-lint-skips-uncommitted-work.md`

  prints a one-line `skip` inside an otherwise green suite, and the same lint then fires in CI.
- **Cross-link + guardrail status** on `verify-row-must-be-pipe-free-and-under-60s.md`: its

### Rationale

The failure is worth a record because the guardrail already existed and still did not protect: the
gap was reachability, not detection. That distinction is what a future author needs — the fix is
to run the file-scoped gates against the path, not to write another lint.

The root cause in the record is the one I proved, not the one I first assumed. My initial
hypothesis was the familiar "no base ref locally" story; `resolve-base-ref.sh` resolves fine here.
Running the same lint invocation against one identical file, uncommitted then committed, produced
`skip` and then the real error — that experiment is what the record documents.

### Alternatives considered

- **Fold it into the existing verify-row record** — rejected; the existing record is about how to
  *write* a row, this one is about why a correct lint did not *run*. Different applicable-when, so
  a reader hitting the green-then-red symptom would not find it there. Cross-linked both ways
  instead.
- **Fix the loud-skip guardrail now** — rejected; it edits `scripts/run-tests.sh`, a high-blast
  path, which would turn a docs commit into a high-risk change. Filed in the backlog where the
  other ratchets live.
